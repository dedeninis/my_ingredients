## 快速開始

直接打開 https://dedeninis.github.io/my_ingredients/ 即可使用，不需要註冊或登入。

**手機建議用瀏覽器的「加到主畫面」安裝。**已具備 PWA 的 manifest 與 service worker，安裝後會以獨立視窗開啟（無網址列），且**斷網時仍可開啟並操作**——瀏覽、新增、修改、刪除、搜尋、採買與到期狀態都不需要網路（PRD 12）。只有雲端同步需要連線。

本機開發時直接用瀏覽器打開 `index.html` 就行，不需要安裝任何東西或啟動伺服器。

> 注意：用 `file://` 開啟和用線上網址開啟，瀏覽器視為**兩個不同的來源**，資料不共通。要讓兩邊看到同一份資料，需要設定雲端同步。

## 功能說明

### 首頁

由上而下是冰箱現況、即將到期的食材、今日料理建議、**美食日誌預覽**、依存放位置（冷藏／冷凍／常溫）分區入口，以及快速操作。

日誌預覽顯示最近一篇記錄的縮圖、料理名稱與用了哪些食材，點下去直接進日誌清單。這個區塊是刻意加的：日誌原本只藏在快速操作的一顆小按鈕裡，跟已記錄的內容毫無視覺連結，回到首頁完全看不到自己記錄過什麼，容易變成沒人想維護的功能。有預覽在，才會形成「看得到成果」的回訪誘因。沒有任何日誌時顯示引導文字，點下去一樣能進日誌清單開始寫第一篇。

依 PRD 7.1，首頁**刻意不顯示食材總數或任何統計圖表**，只用文字描述目前狀態（例如「有食材已過期，建議先處理」）。

有即將到期或已過期的食材時，「即將到期」卡片會緩慢脈動提醒你，尊重系統的減少動態效果偏好（`prefers-reduced-motion`）自動關閉動畫。

### 食材庫存

- 預設排序：已過期 → 今天到期 → 即將到期 → 一般食材；同狀態下最近新增的優先
- 可依**存放位置**或**食材類型**篩選，可搜尋名稱與類型
- 兩排篩選共存但不疊加：選了類型會重置位置，選了位置會重置類型，兩者不會 AND 在一起。類型改名時篩選會跟著轉，類型被刪除時篩選安全重置為全部
- 點任一筆進入詳細頁，可編輯、標記**用完了**，或刪除紀錄（都需二次確認）

### 新增食材

新增頁是所有輸入方式的統一入口（PRD 5.1），最上方可切換**手動、條碼、拍照、語音**。語音尚未實作，按鈕為停用狀態。

六個必填欄位：名稱、食材類型、存放位置、數量、單位、保存期限。缺任何一項都不會寫入，並會指出缺哪一欄。另有選填的商品條碼欄位。

條碼模式辨識成功後會自動切回手動模式並帶入資料，讓你補齊數量與保存期限。離開新增頁或切換到其他模式時，相機一定會關閉。

### 用完了與食材記憶

**每次存檔都會學習**，不只在用完時。記住的是分類、單位、存放位置，以及**慣用保存天數**。

保存天數是最有價值的一項：六個必填欄位裡，期限最難填，卻是這個 App 存在的理由。系統會記下每次「加入當下到到期日」的天數，保留最近 5 筆取中位數，下次新增同名食材就預填「今天 + 中位數天數」，並註明是推估值請你確認。取中位數而非平均，是為了避免單次特例把估計帶偏。

實際效果是六個必填欄位縮到「名稱 + 數量」，其餘自動。

詳細頁的主要動作是「**用完了**」而不是刪除，標記用完會移出庫存並同時更新記憶。名稱欄位提供已記住食材的建議清單。

已填寫的欄位不會被覆寫，只補空的。這份記憶會跨裝置同步，同樣採合併不覆蓋——且**保存天數的樣本會合併而非覆蓋**：兩台裝置各自學到的觀察值會取聯集去重，只留最近 5 筆，不會因為同步就讓其中一邊學到的資料憑空消失。設定頁可查看每項記住的天數，並**單筆移除**打錯的紀錄。

記憶對**所有輸入方式**都生效——條碼、發票、採買清單帶入的名稱一樣會自動補齊欄位。

另外保留「刪除這筆紀錄」，用於移除誤建的資料——**刪除不會寫入記憶**，打錯的名稱不會被學起來。

### 今日料理建議

首頁的「🍳 今日料理建議」會依冰箱現有食材比對常見家常菜，點進去看完整清單。

依 PRD 10.2，每則建議只包含**料理名稱、可使用的庫存食材、優先使用原因**三項，不提供烹調步驟、調味比例或營養資訊。

比對方式分三層：先用食材名稱的關鍵字比對（例如「番茄 + 蛋」→ 番茄炒蛋），沒命中時用食材類型組合保底（例如「蔬菜 + 蛋類」→ 蔬菜烘蛋，或單一「肉類」→ 香煎肉排），**兩層都沒有結果、且已設定 Gemini 金鑰時**，才呼叫 AI 依現有食材產生建議。排序上，能用掉越多即將到期食材的排越前面；同一個條件有多樣食材可選時，優先挑最快到期的那樣。

AI 備援只會在**進入「今日料理建議」頁面**時觸發，首頁摘要一律只用本機規則，不會因為頻繁開啟首頁就默默連線出去。同一份庫存不會重複呼叫，庫存變動才會重新詢問。模型只能從目前庫存的食材裡挑，回傳裡引用清單外食材的整道建議會被捨棄，不會顯示「用了冰箱裡沒有的東西」這種不實資訊。頁面上會清楚標示「本機規則沒有比對到結果，以上是 Gemini 依現有食材提供的建議（已將食材名稱與到期狀態傳送至 Google）」，呼叫失敗時也會顯示原因而不是卡住不動。

**已過期的食材不會被列入建議。**

每則建議的料理名稱右側有「參考食譜」文字與三個搜尋捷徑，點了在新分頁打開該平台對這道料理的搜尋結果，方便查作法。三個網址格式都實際確認過會出現對應搜尋結果。捷徑以平台名稱文字呈現（YouTube／Cookpad／愛料理），而非圖示——2026-08-03 因原本用 emoji（▶️🍳🍚）不直覺、看不出對應哪個網站而改。沒有直接採用各平台官方 Logo，是因為那屬於商標資產，第三方 App 不能任意嵌入使用；文字則不受此限制，辨識度也更高。

目前完全在本機比對，不呼叫任何外部服務、不需要 API 金鑰，離線可用。`getSuggestions()` 保持非同步介面，日後要改接 AI 時只需替換該函式的實作，呼叫端不必更動。

### 拍照辨識

新增頁切到「拍照」分頁。有兩顆按鈕：「📷 拍照」與「🖼 從相簿選」，分開是刻意的——`<input type="file" capture="environment">` 的 `capture` 屬性不是硬性規定，只是提示，各瀏覽器解讀不一致，MDN 明確標記這不是 Baseline 功能：有的瀏覽器會直接強制開相機、完全跳過相簿，有的則忽略這個提示。同一顆按鈕在不同瀏覽器上會有不同行為，所以拆成兩顆各自明確對應，不依賴瀏覽器怎麼解讀。可以拍**單一食材或包裝**，也可以拍**整張購物發票**，由模型自行判斷是哪一種——使用者不必先替自己的照片分類。

拍**包裝**時會試著讀出上面的有效期限，這是條碼與發票都給不了的欄位，也是這個功能最有價值的地方。辨識成功會直接進入表單讓你確認。

拍**發票**時會辨識出食材清單。辨識結果是一份工作清單，逐項點「加入」帶進表單確認後儲存，加完會自動回到清單處理下一項。**清單會保存在本機**，關掉分頁或切去別的 App 都不會遺失，避免十樣東西的發票加到一半整份消失還得重花一次辨識額度。

**這不是自動建檔。**發票能提供的只有名稱與數量，六個必填欄位裡的分類、單位、存放位置都要你補，而**保存期限發票永遠不會有** —— 那是這個 App 的核心欄位。它省下的是打名稱的工，定位是「採買清單的反向操作」：買完之後一次帶入。

品名會請模型還原成看得懂的名稱（賣場常見的「蔬-青江菜」會還原成青江菜），並自動略過衛生紙、清潔用品等非食品。

美食日誌的「照片（選填）」也是同樣的兩顆按鈕設計。

#### 設定與費用

到設定頁「拍照辨識」填入 Gemini API 金鑰。模型預設 `gemini-3.5-flash`。

**模型會隨時間汰換。**舊世代失去免費層配額後，Google 回的是 **429**，訊息看起來像「用超量」，但內容裡其實是 `quota_value: 0` —— 意思是這個模型在你的專案根本沒有額度，不是你用完了。第一次呼叫就拿到 429 幾乎都是這個原因。

設定頁有「**測試連線並列出可用模型**」，會列出這把金鑰當下真正能呼叫的模型，點一下即可套用。遇到問題先按這個，不要猜模型名稱。已存的 `gemini-1.x` / `gemini-2.x` 會在載入時自動升級到預設模型。

> **照片會傳送到 Google。**發票尤其敏感，它揭露你買了什麼、在哪買、幾點買。App 不保存照片，但傳送這件事本身需要你知情（PRD 10.3）。
>
> **金鑰只存在這台裝置，不會被同步到 Gist** —— 存在獨立的 `ingredient-manager-v1-ai`，不進同步內容。換裝置要重新輸入。
>
> 強烈建議到 Google Cloud Console 為金鑰設定**參照網址限制**與**每日配額上限**。參照網址可被非瀏覽器客戶端偽造，所以限制不等於保密；真正兜底的是配額上限。

上傳前會先把照片縮到長邊 1600px 的 JPEG，省流量也省費用。

### 美食日誌

首頁「美食日誌」開啟日誌清單，右上角「＋」寫新的一篇：選日期（預設今天）、輸入料理名稱、從目前庫存**多選**用掉的食材。每項食材勾選後可以填「用了多少」，預設帶入目前庫存的全部數量，也可以改小：填的量等於庫存全部就整列移除，填得比庫存少就從庫存扣減、保留剩下的部分——不是勾了就整批清空。可選填「心得筆記」文字（調味心得、失敗經驗都可以，2026-08-03 新增）與一張照片。存檔後照樣餵進食材記憶（保存天數學習照跑），不論這次是整列用完還是只用一部分。

有心得筆記時，首頁的日誌預覽會優先顯示筆記內容而不是用了哪些食材；沒有筆記才退回顯示食材清單。日誌清單（一列一列的列表）維持只顯示菜名與日期，沒有加筆記摘要。

#### 分享

日誌詳細頁若瀏覽器支援，會出現分享按鈕，呼叫瀏覽器內建的 `navigator.share()` 叫出系統原生的分享選單（LINE、訊息、Email...），把**照片與料理名稱**交給你選的那個 App，不含日期、食材列表與心得筆記。圖示原本是 📤 emoji，後來改成手畫的 SVG，2026-08-03 再改成跟參考食譜捷徑一樣的純文字膠囊按鈕（「分享」二字），全站圖示風格統一為文字優先，避免 emoji／圖示辨識度不足的問題。

帶照片時，`title`／`text` 這兩個欄位會不會顯示、顯示在哪，完全由接收端 App 自己決定（規格本身就這樣寫），LINE 等 App 常見的行為是圖片直接進聊天室、文字卻不見。只留 `text`、不填 `title` 是已知能改善這個狀況的作法，本 App 採用這個做法。**實機測試過分享到 LINE：改了之後仍然沒有帶出名稱**，確認這是 LINE 收到圖片時的處理方式、不是網頁這端能修的問題，之後不再嘗試修正，細節見 TODO.md。**照片是裝置對裝置直接傳遞，不會經過任何伺服器**，跟這個 App 一路以來「本機優先」的原則一致，也不需要新增任何後端。

支援狀況：Android Chrome、iOS Safari、桌面 Chrome／Safari 都支援；**Firefox 目前不支援**（規格本身標記為非 Baseline 功能）。偵測不到 `navigator.share` 時按鈕直接不顯示，不會出現一顆按下去必定失敗的按鈕。若瀏覽器支援分享文字但不支援夾帶照片檔案，會自動退回純文字分享而不是整個分享失敗；使用者在系統分享選單按取消不會顯示任何錯誤提示。

#### 編輯已存的日誌

日誌詳細頁有「✏️ 編輯」，可以改日期、料理名稱與照片。**已經記錄的食材無法在編輯時移除**——因為存檔當下就已經把它從庫存扣掉，只留了名稱和分類快照，沒有足夠的資料能安全「還原」回庫存（正確的數量、單位、到期日都已經不在了）。編輯畫面下方的食材選單只列出**目前庫存還有的**項目，用來追加漏記的食材（例如忘記勾的配料），選了一樣會照存檔當下的邏輯扣庫存。真的記錯到需要整篇重寫，用詳細頁的「刪除這篇日誌」整篇砍掉重寫比較乾淨。

跟「用完了」是並存關係：單純用掉一樣東西還是走詳細頁的快速按鈕，一次做一道菜牽涉好幾樣食材時走日誌。清單以照片縮圖排列，點進去看單篇詳細內容（日期、可搜尋作法的料理名稱、用了哪些食材），可個別刪除。

「今日料理建議」的每張卡片也有「📓 加入美食日誌」按鈕，點了會帶著料理名稱與建議用到的食材直接開日誌表單並預先勾選——但只是**預填**，日期、名稱、勾選的食材到存檔前都能自由修改，真正扣庫存與寫入日誌仍要按下「儲存日誌」才會發生。若建議產生後食材被刪除或編輯過，開表單時只會預先勾選當下仍在庫存裡的項目，不會帶進不存在的食材。這個按鈕本機規則與 AI 動態建議兩種來源的卡片都適用。

#### 照片存放與同步

日誌的文字內容（日期、料理名稱、用了哪些食材）跟一般資料一樣走 localStorage 並同步；**照片是大型二進位資料，改存 IndexedDB，這是這個 App 第一次用到它**，且刻意不跟著同步——同步機制是把整包 JSON 塞進一個 Gist，base64 內嵌照片會讓檔案暴增、同步變慢。所以文字紀錄跨裝置都看得到，但照片只留在拍攝的那台裝置：手機拍的照片，電腦看得到這篇日誌，但看不到照片，縮圖會顯示預設圖示而非壞圖或報錯。

上傳前一樣會壓縮（長邊 1400px），但畫質留得比辨識用的縮圖高一些，因為這是要回頭看的紀錄，不是用完即丟。

### 條碼掃描

新增頁切到「條碼」分頁，或從首頁按「掃描條碼」直接進入，對準商品條碼即可。**相機掃描需要 Android Chrome**（使用瀏覽器內建的 `BarcodeDetector`）；iOS Safari 沒有這項功能，會退回手動輸入條碼號碼。不引入額外的解碼函式庫。

流程分三層：

1. **店內碼**（`020-029`、`200-299` 開頭）→ 直接說明「賣場現場秤重標籤，只在該店有效且內含價格」並轉手動填寫，不做記憶
2. **條碼記錄命中** → 帶出名稱、類型、單位與存放位置，你只要填數量與保存期限
3. **沒有紀錄** → 手動填寫，存檔後記住這組條碼

保存期限一律留空，條碼不可能知道這個。

條碼會存在食材紀錄上，新增與編輯表單都有「商品條碼（選填）」欄位，詳細頁也看得到。因此**編輯食材改名時，條碼記錄會同步更正** —— 掃錯或打錯名稱不會永久卡在記錄裡。條碼欄位也可自行輸入或清空，清空只解除該筆食材的關聯，不影響已記住的條碼。

#### 條碼記錄會跨裝置共用

記住的條碼會隨雲端同步共用給所有裝置，而且**採合併而非覆蓋** —— 手機學到的和電腦學到的都會保留，即使庫存那邊發生衝突也不受影響。條碼在全台通用且終身不變，所以這份記錄不會過期，命中率只會隨使用時間上升。

> **為什麼不接商品資料庫？**
> Open Food Facts 只收錄約 3,000 筆台灣商品（日本有 42,000 筆），而全聯、家樂福的現場秤重生鮮用的是店內碼，任何外部資料庫都不可能有。相較之下，記住你自己買過的商品命中率高得多，且完全離線。日後要接外部資料庫可以加在第 2 與第 3 層之間。

#### 為什麼用完整條碼當鍵

GS1 的廠商識別碼是變動長度（6 到 10 碼不等，依廠商申請的商品數量核發），**光看條碼無法判斷廠商碼在哪結束**。因此不做任何拆解或前綴聚合，一律完整比對。UPC-A（12 碼）會補前導 0 正規化成 13 碼，否則同一項進口商品會被存成兩筆。

### 採買清單

- 新增待購項目（名稱、數量、單位、備註）
- 買到後勾選，狀態變成「已購買」
- 按「轉為庫存」會帶著名稱、數量、單位開啟新增表單，**類型、位置與保存期限留空要求你補齊**，補完才會寫入庫存
- 也可以只勾選標記完成，不轉入庫存

轉入後的食材來源會記為「採買清單轉入」，採買項目狀態變成「已加入庫存」且不可再編輯。

### 設定

- **外觀**：冰箱名稱自訂、介面深淺（跟隨系統／淺色／深色）
- **到期提醒**：開關與系統通知權限狀態
- **食材類型**：新增自訂類型、重新命名（會一併搬移既有食材）、刪除（使用中的類型不允許刪除）
- **資料管理**：分別清除庫存、採買清單、條碼記錄與食材記憶，各需二次確認
- **拍照辨識**：Gemini 金鑰、模型選擇、測試連線
- **雲端同步**：見下一節
- **關於**：版本與隱私說明

## 雲端同步設定

透過 GitHub Secret Gist 讓多台裝置共用同一份資料。**這是選用功能**，不設定的話 App 完全正常運作，資料只留在該裝置。

### 設定步驟

1. 建立一個 Secret Gist，檔名 `my-ingredients.json`，內容填 `{}`
2. 記下網址最後那段 32 字元的 **Gist ID**（不要包含前面的網址）
3. 到 [GitHub Token 設定](https://github.com/settings/tokens) 建立 classic token，**Scopes 只勾 `gist`**
4. 打開 App → 設定 ⚙️ → 雲端同步 → 填入 Gist ID 與 Token → 儲存設定

其他裝置重複第 4 步即可。

### 同步行為

- 開啟頁面時自動拉取雲端資料
- 資料變動後約 2.5 秒自動上傳（合併連續操作，避免頻繁呼叫 API）
- 設定頁有「立即同步」按鈕與最後同步時間
- 同步內容：庫存、採買清單、食材類型與偏好、條碼記錄、食材記憶
- 提醒排程**不同步**，它由庫存推導，拉取後本機自動重建

### 衝突處理

兩台裝置都改過同一份資料時，**不會自動覆蓋**。App 會跳出對話框顯示雙方最後修改時間，讓你選擇：

- 用雲端覆蓋本機
- 用本機覆蓋雲端
- 先不同步（兩邊都保持原樣）

### 安全須知

> **Token 只存在你自己的裝置**，寫在該瀏覽器的 localStorage，不會被放進同步內容，也不在原始碼裡。換裝置需要重新輸入。
>
> **不要把 Token 或 Gist ID commit 進這個 repo。** 本 repo 是公開的，Secret Gist 僅靠網址難以猜測來保護，ID 一旦公開等於庫存內容公開。
>
> **Secret Gist 不等於私密。** 任何取得該網址的人都能讀取內容。若需要真正的私密性，應改用 private repo 搭配 Contents API。

## 到期提醒與其限制

依 PRD 11，每筆食材會自動建立兩個提醒排程：**到期前 3 天**與**到期當天**。新增、修改保存期限或刪除食材時，排程會同步建立、更新或取消。

通知文案：

```
食材提醒：牛奶將於 3 天後到期，建議優先使用。
食材提醒：青菜今天到期，請確認是否需要使用。
```

### 網頁版的硬限制

**App 沒開啟時無法主動通知你。** 這是瀏覽器的能力限制，不是實作問題 —— 網頁沒有可靠的本機排程通知 API（iOS 尤其沒有）。

實際行為是：你**開啟頁面時**，會收到當下該收的提醒。已過期的食材不再發通知，改由首頁與清單優先顯示。同一項食材一次只送一則，不會因為兩個排程同時到期而重複。

關閉提醒或未授權通知權限時，首頁與清單的到期狀態**照常顯示**。

若之後需要真正的背景通知，得改用 Capacitor 之類的原生封裝。

## 資料存放

全部存在瀏覽器的 localStorage：

| Key | 內容 |
|---|---|
| `ingredient-manager-v1-items` | 食材庫存 |
| `ingredient-manager-v1-shopping-items` | 採買清單 |
| `ingredient-manager-v1-settings` | 食材類型與提醒偏好 |
| `ingredient-manager-v1-reminders` | 提醒排程（由庫存推導，不同步） |
| `ingredient-manager-v1-products` | 條碼記錄（同步，整筆合併不覆蓋） |
| `ingredient-manager-v1-known` | 食材記憶：名稱→分類／單位／位置／保存天數（同步，**保存天數樣本合併**，其餘欄位取新的） |
| `ingredient-manager-v1-food-log` | 美食日誌文字內容（同步，依 id 合併） |
| IndexedDB `ingredient-manager-v1-photos` | 日誌照片（**不同步**，只留在拍攝的裝置） |
| `ingredient-manager-v1-photo-draft` | 拍照辨識的待處理清單（本機工作狀態，不同步） |
| `ingredient-manager-v1-sync` | 同步設定含 Token，**永不上傳** |
| `ingredient-manager-v1-ai` | Gemini 金鑰與模型，**永不上傳** |

### 資料模型

**食材（InventoryItem）**

`id`、`name`、`category`、`quantity`、`unit`、`storageLocation`（冷藏／冷凍／常溫）、`expiryDate`、`barcode`（選填）、`source`（`manual` / `photo_ai` / `barcode` / `voice` / `shopping_draft`）、`createdAt`、`updatedAt`

**美食日誌項目（LogItem，記在 FoodLogEntry.items 裡）**

`name`、`category`、`quantity`（實際用掉的量）、`unit`。舊資料若在這次改動前建立，可能沒有 `quantity`／`unit`，畫面上會自動省略數量顯示，不影響其他功能。

**採買項目（ShoppingItem）**

`id`、`name`、`quantity`、`unit`、`note`、`status`（`pending` / `purchased` / `converted`）、`inventoryDraftId`、`createdAt`、`updatedAt`

**提醒排程（ReminderSchedule）**

`id`、`inventoryItemId`、`reminderType`（`three_days_before` / `expiry_day`）、`scheduledAt`、`status`（`scheduled` / `sent` / `cancelled`）

⚠️ **沒有備份機制。** 清除瀏覽器資料會讓庫存永久消失（除非已設定雲端同步）。

## 技術架構

```
index.html              App 本體，HTML／CSS／JS 全部內嵌
sw.js                   Service worker，負責離線快取
manifest.webmanifest    PWA 設定
icon-192.png            圖示（由 tools/make-icons.py 產生）
icon-512.png
tools/make-icons.py     圖示產生腳本
```

`index.html` 約 1,580 行。

- **無框架、無建置流程、無相依套件** —— 打開檔案就能跑
- 單一 `setView()` 以 `renderers` 表分派各頁面
- 所有寫入集中在 `saveItems` / `saveShoppingItems` / `saveSettings`，同步的髒資料標記統一在這裡處理
- 確認對話框統一走 `askConfirm({ title, text, confirmLabel, onConfirm })`，每次重設全部文字

這個選擇是刻意的：規模還小，額外的建置工具只會增加負擔。等到要接入 AI 或條碼掃描等外部相依時，再考慮模組化與打包。

### 已知限制：單筆刪除與同步的先後順序

條碼記錄、食材記憶、美食日誌都是「合併不覆蓋」的字典型資料，同步時是把雲端有、本機沒有的補進來。這表示**如果先刪除單一筆、還沒等到那次刪除同步出去，就手動再按一次「立即同步」**，雲端那筆舊資料可能會被拉回來、蓋掉你剛才的刪除。實務上影響很小（背景會在幾秒內自動推送刪除結果），但了解這個限制比較不會被少見的巧合搞混淆。

### 部署後要注意

改動 `index.html` 後，**要把 `sw.js` 裡的 `CACHE` 版本號往上加**，否則已安裝的使用者可能繼續拿到舊版。頁面本身採 network-first，一般情況會自動更新，但版本號才是可靠的作法。

料理建議選擇規則式而非 AI，是因為 PRD 10.2 對輸出的要求僅為名稱、可用食材與優先原因，本機比對即可滿足，同時保有離線能力（PRD 12）且不需傳送任何資料到外部（PRD 2.3、10.3）。

AI 供應商已決定為 Google Gemini（PRD 附錄 C 第 3 項）。金鑰由使用者在設定頁輸入，存於獨立的儲存項目，不進同步內容。語音沿用同一套接法即可，或先做規則式解析。

例外是**條碼掃描**——可用瀏覽器內建的 `BarcodeDetector` 搭配 Open Food Facts 等免金鑰的開放商品資料庫，不需要碰供應商問題，是目前最容易推進的一項。

### Could — 全部完成

自訂食材類型（含改名）、提醒開關、資料清除。

### 與 PRD 的已知差異

- **雲端同步**：PRD 4.2 將雲端同步列為 V1.0 不包含項目，此處依實際需求提前實作。無帳號、無伺服器，僅為選用的資料轉移機制。
- **條碼記錄**：PRD 4.2 排除「條碼找不到商品時的自建商品資料庫」。但查證後發現外部資料庫對台灣商品幾乎無用（見上方說明），若照原規格實作，條碼掃描在台灣情境下沒有實際價值，因此改為記住使用者自己建立的商品。
- **食材類型刪除**：PRD 7.9 只要求「查看、改名與新增」，此處額外允許刪除未被使用的自訂類型。

## 已知限制

- **無備份**：清除瀏覽器資料即遺失，除非已設定雲端同步
